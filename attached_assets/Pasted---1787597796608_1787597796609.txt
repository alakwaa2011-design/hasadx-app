 أساس وكيل واتساب شخصي خاص داخل حصاد

الهدف

ابنِ أساساً آمناً ومغلقاً لوكيل واتساب شخصي يخص المالك مروان فقط، داخل مشروع حصاد الموجود حالياً. سيستخدم لاحقاً رقم واتساب مستقل وتطبيق Meta الذي أُنشئ باسم Marwan Personal Assistant، لكن لا تربط رقم واتساب الآن، ولا ترسل أو تستقبل أي رسالة حية، ولا تطلب أي أسرار.

هذه وحدة إدارية خاصة بالمالك، وليست ميزة لمنصة حصاد التعليمية، ولا تظهر للمعلمين أو المتعلمين أو الزوار.

نطاق غير قابل للتفاوض

ما يُسمح به

1.
فحص بنية الخادم الحالية ونمط المصادقة ومسارات الإدارة الحالية قبل التعديل.

2.
إنشاء صفحة إدارة خاصة بالمالك فقط باسم «مساعد مروان الشخصي»، داخل مساحة الإدارة القائمة أو على مسار إداري واضح ومتسق مع المشروع.

3.
إنشاء مسار ويبهوك عام مخصص لـMeta بالشكل التالي فقط:

Plain Text


/api/webhooks/whatsapp





4.
إنشاء جداول/هجرات منفصلة للوحدة الشخصية فقط إن كان التخزين ضرورياً، مثل:

استخدم تسميات المشروع الفعلية إن كانت مختلفة، لكن لا تعدّل أي جدول قائم لمنصة حصاد ولا تضف أعمدة إلى جداول المعلمين أو المستخدمين أو الأنشطة.

•
personal_assistant_threads

•
personal_assistant_messages

•
personal_assistant_actions



5.
إنشاء عميل WhatsApp معطل افتراضياً (dry-run) ووضع طبقة إعدادات معزولة، بحيث لا يمكنه إرسال أي طلب خارجي أو رسالة إلا عند تفعيل صريح مستقبلي.

6.
إنشاء اختبارات خادم وواجهة مناسبة للنطاق، ثم تقديم تقرير ولقطات معاينة إدارية فقط.

ما يمنع منعاً باتاً

•
لا تعدّل أي لعبة أو واجب أو عرض أو مكتبة أو صفحة معلّم أو صفحة متعلم أو صفحة عامة.

•
لا تقرأ أو تستخدم بيانات المعلمين أو المتعلمين أو الفصول أو الأنشطة أو العروض لصالح الوكيل.

•
لا تستخدم CreditService أو نقاط حصاد أو XP أو الباقات أو Lemon Squeezy أو Webhooks الدفع أو أي مفتاح دفع.

•
لا تغيّر التسعير أو قاعدة البيانات الحالية أو واجهات API الحالية أو الأسرار الحالية أو إعدادات النشر.

•
لا تضف رابطاً في قوائم المعلّم أو المتعلم أو الجوال أو الصفحة العامة.

•
لا تربط رقم واتساب، ولا ترسل رسالة اختبار حية، ولا تستدعي Meta أو نموذج ذكاء اصطناعي حياً، ولا تطلب مفاتيح أو رموزاً في هذه المهمة.

•
لا تنشر.

1. فحص مسبق إلزامي قبل أي تعديل

اعرض أولاً في التقرير الداخلي المختصر:

1.
أين تُعرّف المصادقة الخادمية وصلاحية المسؤول فعلياً في هذا المشروع؟ افحصها أولاً، ولا تنشئ تعريف مسؤول موازياً بالواجهة فقط.

2.
ما نمط مسارات الخادم الحالي، وما الملف الأنسب لإضافة GET وPOST للويبهوك من دون التأثير في المسارات القائمة؟

3.
ما أداة migration والجداول الموجودة التي يستخدمها المشروع؟

4.
ما صفحات الإدارة الموجودة فعلاً التي يمكن وضع رابط داخلي صغير للوحدة بداخلها، أو هل يجب أن تكون الصفحة بلا رابط في المرحلة الأولى؟

5.
هل يوجد تكامل ذكاء قائم؟ افحصه قراءة فقط، لكن لا تعِد استخدام مفاتيحه أو رصيده أو مساراته لهذه الوحدة.

إذا ظهر تعارض حقيقي مع منطق قائم، توقف عند التقرير ولا تتجاوز التعارض بافتراضات.

2. عزل الصلاحيات والبيانات

الوصول الإداري

•
لا تعتبر كل admin مالكاً تلقائياً. هذه الوحدة يجب أن تسمح بحسابي مروان الإداريين فقط، لا بكل المسؤولين الحاليين أو المستقبليين.

•
اعتمد على المصادقة الخادمية القائمة أولاً، ثم طبّق طبقة وصول إضافية معزولة قائمة على معرّفات الحساب الداخلية الموثوقة فقط.

•
أضف إعداداً بيئياً مستقلاً باسم PERSONAL_ASSISTANT_OWNER_ACCOUNT_IDS يقبل قائمة مفصولة بفواصل لمعرّفي الحسابين الداخليين. لا تضع أي قيمة فعلية في الكود أو الاختبارات أو السجلات أو التقرير.

•
لا تعتمد على البريد أو الاسم أو لقب الدور وحده، ولا تكتب أي معرف حساب ثابت في المصدر.

•
الصفحة الإدارية والـAPI الإداري للوحدة لا يعملان إلا لمستخدم مصادق عليه خادمياً ومعرّفه ضمن قائمة PERSONAL_ASSISTANT_OWNER_ACCOUNT_IDS بعد تطبيعها.

•
عند غياب الإعداد أو كونه فارغاً، تبقى الوحدة مقفلة بأمان وتعيد 403، ولا تفترض أن جميع المسؤولين مخولون.

•
أي مستخدم غير مصرح له يحصل على 403 خادمياً، وليس مجرد إخفاء واجهة.

•
لا تعرض الوحدة في قائمة التنقل العامة أو المعلم أو المتعلم.

التخزين

•
استخرج وخزّن الحد الأدنى فقط: هوية محادثة واتساب، اتجاه الرسالة، نص الرسالة، وقتها، معرف رسالة Meta الخارجي، وحالة المهمة/الموافقة.

•
لا تخزّن payload الويبهوك كاملاً بعد إتمام التحقق من التوقيع، ولا تسجله في السجلات؛ احتفظ فقط بالحقول الدنيا اللازمة لهذه الوحدة.

•
لا تخزّن أسراراً أو رموز وصول في الجداول.

•
لا تنسخ أي بيانات من حصاد إلى جداول الوحدة.

•
اجعل آلية حذف محادثة أو مسح سجل واضحة داخل الصفحة الإدارية، لكن لا تنفذ حذفاً جماعياً أو بيانات اختبار حقيقية.

3. إعدادات منفصلة تماماً

أضف أسماء الإعدادات التالية إلى توثيق البيئة فقط، ولا تضع لها قيماً ولا تكتبها في السجل:

Plain Text


PERSONAL_ASSISTANT_OWNER_PHONE
PERSONAL_ASSISTANT_OWNER_ACCOUNT_IDS
PERSONAL_ASSISTANT_WHATSAPP_VERIFY_TOKEN
PERSONAL_ASSISTANT_WHATSAPP_APP_SECRET
PERSONAL_ASSISTANT_WHATSAPP_ACCESS_TOKEN
PERSONAL_ASSISTANT_WHATSAPP_PHONE_NUMBER_ID
PERSONAL_ASSISTANT_OUTBOUND_ENABLED=false
PERSONAL_ASSISTANT_AI_ENABLED=false



القواعد:

•
استعمل هذا الـprefix فقط؛ لا تعِد تسمية أو تعديل أي متغير Meta/WhatsApp موجود قد يخص حصاد مستقبلاً.

•
PERSONAL_ASSISTANT_OWNER_ACCOUNT_IDS يضم معرّفي حسابي المالك الداخليين فقط بصيغة قائمة مفصولة بفواصل؛ لا تستخدم البريد أو الاسم، ولا تكشف القيم في الواجهة أو التقرير.

•
لا تكشف وجود السر أو قيمته في الواجهة أو الاختبارات أو السجلات.

•
عند غياب أي إعداد، اعرض في لوحة المالك حالة آمنة مثل «غير مهيأ بعد»، ولا ترسل طلباً خارجياً.

4. ويبهوك Meta — أساس آمن فقط

أنشئ المسار /api/webhooks/whatsapp كما يلي:

GET: التحقق

•
يدعم تحقق Meta القياسي عبر hub.mode وhub.verify_token وhub.challenge.

•
لا يعيد hub.challenge إلا إذا تطابق رمز التحقق مع PERSONAL_ASSISTANT_WHATSAPP_VERIFY_TOKEN.

•
عند الخطأ يعيد 403 بلا كشف الرمز أو تفاصيل حساسة.

POST: استقبال الرسائل

•
تحقّق من توقيع X-Hub-Signature-256 باستخدام HMAC-SHA256 ومفتاح PERSONAL_ASSISTANT_WHATSAPP_APP_SECRET قبل معالجة أي جسم طلب.

•
استخدم الجسم الخام فقط داخل الذاكرة لحساب التوقيع عند الحاجة، ولا تخزّنه أو تسجله كاملاً بعد انتهاء التحقق.

•
اقبل الرسائل النصية فقط في النسخة الأولى.

•
لا تقبل الرسائل إلا إذا جاء المرسل من الرقم المحدد في PERSONAL_ASSISTANT_OWNER_PHONE بعد تطبيع صيغة الرقم. أي رقم آخر بعد نجاح التوقيع: تجاهله بأمان، ولا تنشئ له محادثة أو مهمة ولا ترد عليه، وأعد نجاحاً صامتاً مناسباً لمنع إعادة التسليم وعدم كشف سياسة الوصول.

•
امنع التكرار على مستوى قاعدة البيانات بقيد UNIQUE على external_message_id أو آلية ذرية مكافئة، وليس بفحص على مستوى التطبيق فقط.

•
عند وصول رسالة صحيحة من المالك، خزّنها وأنشئ مهمة داخلية بحالة pending_review أو pending_confirmation؛ لا تنفذ حجزاً أو مراسلة أو دفعاً أو بحثاً خارجياً.

5. العميل الخارجي وسلوك النسخة الأولى

•
أنشئ طبقة عميل منفصلة لرسائل WhatsApp قابلة للاختبار بالـmock.

•
يجب أن تكون PERSONAL_ASSISTANT_OUTBOUND_ENABLED=false افتراضياً. في هذه الحالة لا ينفذ العميل fetch أو أي إرسال شبكي، ويكتفي بتسجيل محاولة داخلية آمنة للحالة/الاختبار.

•
لا تفعل PERSONAL_ASSISTANT_AI_ENABLED الآن، ولا تستخدم رصيد حصاد أو نماذجه أو أي خدمة ذكاء قائمة.

•
صمّم حالات المهمة فقط:

الحالة
المعنى
received
وصلت رسالة المالك وتحققت سلامتها.
pending_review
تنتظر مراجعة المالك من لوحة الإدارة.
pending_confirmation
جهز الوكيل لاحقاً ملخصاً ويحتاج كلمة «أكّد».
confirmed
وافق المالك، لكن لا ينفذ خارجياً في هذه المرحلة.
cancelled
ألغى المالك الطلب.






انتقالات الحالات

•
كل انتقال حالة يجب أن ينفذ خادمياً عبر دالة/سياسة انتقال محددة، ولا تثق بقيمة حالة يرسلها العميل.

•
زر «اعتماد» في هذه المرحلة يسمح بالانتقال من الحالة المسموح بها إلى confirmed فقط، ولا يستدعي أي executor أو ذكاء اصطناعي أو WhatsApp أو HTTP خارجي.

•
لا تسمح بإحياء مهمة cancelled أو بأي انتقال غير صحيح، إلا عبر منطق صريح مؤجل لمرحلة مستقبلية.

6. واجهة «مساعد مروان الشخصي»

صمم صفحة إدارية RTL خفيفة ومتسقة مع هوية حصاد، لكن لا تقدّمها كأداة للمعلمين. يجب أن تتضمن:

1.
عنوان واضح: «مساعد مروان الشخصي» ووصف دقيق: «وحدة خاصة لإدارة طلباتك الواردة عبر واتساب».

2.
حالة التهيئة: رقم المالك موجود/غير موجود، التحقق مهيأ/غير مهيأ، الإرسال الخارجي مغلق دائماً في هذه المرحلة.

3.
قائمة محادثات خاصة فارغة عند عدم وجود بيانات، من دون نماذج رسائل أو أرقام وهمية.

4.
قائمة طلبات/مهام، مع أزرار إدارية واضحة: «اعتماد» و«إلغاء». الاعتماد يغير الحالة فقط ولا يرسل رسالة أو ينفذ إجراء خارجياً.

5.
إجراء مسح سجل محمي بتأكيد واضح، إن كان متسقاً مع مكونات المشروع الحالية.

6.
لا تضع عناصر مزيفة أو حالة «متصل» أو رسائل تجريبية أو إحصاءات غير حقيقية.

7. ضوابط إضافية للأمان والتزامن

•
إذا كشف الفحص المسبق أن أي ضابط في هذا الأمر لا يمكن تحقيقه من دون تعديل نظام مركزي قائم في حصاد، توقف عند التقرير ولا تنفذ workaround يمس المنصة. يُسمح فقط بالإضافة المعزولة PERSONAL_ASSISTANT_OWNER_ACCOUNT_IDS المبينة أعلاه؛ لا تنشئ نظام أدوار مركزي جديداً.

•
اختبر قرار الوصول ضد قائمة حسابي المالك المهيأة خادمياً، ولا تفترض أن دور المسؤول وحده يكفي.

•
اجعل كل عمليات إنشاء الرسالة/المهمة والانتقال بين الحالات آمنة للتزامن وذرية بقدر ما يتيحه نمط قاعدة البيانات الحالي.

8. الاختبارات الإلزامية

أضف اختبارات واقعية مع قاعدة اختبار/Mocks معزولة فقط، وتشمل على الأقل:

1.
GET /api/webhooks/whatsapp يعيد التحدي فقط عند رمز تحقق صحيح ويرفض الرمز الخاطئ.

2.
POST /api/webhooks/whatsapp يرفض توقيع Meta غير الصحيح قبل إنشاء أي سجل.

3.
رسالة صالحة من رقم المالك تنشئ سجلاً واحداً وحالة مهمة صحيحة.

4.
رقم غير المالك لا ينشئ محادثة ولا مهمة ولا رد.

5.
تكرار معرّف رسالة Meta لا يكرر السجل أو المهمة حتى مع طلبين متزامنين.

6.
عند تعطيل الإرسال الخارجي، لا يحدث أي اتصال HTTP خارجي.

7.
API وصفحة الإدارة تسمحان لحسابي المالك الموجودين في إعداد الاختبار المعزول وترفضان أي مسؤول آخر أو مستخدم غير مصرح له خادمياً.

8.
لا يظهر مسار أو رابط الوحدة في قوائم المعلم أو المتعلم أو العامة.

9.
زر الاعتماد لا ينفذ إلا الانتقال الخادمي الصحيح إلى confirmed ولا يستدعي أي خدمة خارجية، ولا يمكن إحياء cancelled.

10.
فحص TypeScript والبناء واختبارات الوحدة ذات الصلة تنجح.

لا تستخدم رقم واتساب حقيقياً أو رموز Meta حقيقية أو مفاتيح سرية في الاختبارات.

9. التقرير المطلوب قبل التوقف

توقف بعد التنفيذ في بيئة المعاينة فقط، ولا تنشر. أرسل تقريراً يتضمن:

1.
الملفات المعدلة والمضافة، مع سبب كل ملف.

2.
أي migration أو جداول جديدة، مع تأكيد عدم تعديل جداول حصاد القائمة.

3.
المسار النهائي للويبهوك الذي سيُدخل لاحقاً في Meta.

4.
قائمة متغيرات البيئة المطلوبة بالاسم فقط، من دون قيم.

5.
نتائج الاختبارات وTypeScript والبناء.

6.
لقطة دخول المالك للصفحة ولقطة رفض وصول مستخدم غير مصرح له إن أمكن عبر بيئة اختبار معزولة.

7.
تأكيد صريح: لم يُربط رقم، ولم تُرسل رسالة، ولم يُمس الدفع أو Lemon أو نقاط حصاد أو بيانات المعلمين أو المتعلمين، ولم يتم النشر.

8.
تقرير صريح عن آلية وصول حسابي المالك الخادمية واسم الإعداد المطلوب، من دون كشف أي معرّفات حساب فعلية.

لا تنشئ مهمة متابعة تلقائية. انتظر المراجعة قبل اقتراح إضافة ذكاء حي أو إرسال واتساب أو ربط الرقم.
