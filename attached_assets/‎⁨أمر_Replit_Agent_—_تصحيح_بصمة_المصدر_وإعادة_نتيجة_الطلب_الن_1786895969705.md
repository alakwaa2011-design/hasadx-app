# أمر Replit Agent — تصحيح بصمة المصدر وإعادة نتيجة الطلب الناجح

التنفيذ الحالي جيد. قبل النشر، صحّح النقطتين التاليتين فقط، من دون تغيير بقية المنطق أو الأسعار أو الواجهة أو مسار الخصم والاسترداد. لا تنشر.

## 1. بصمة المصدر

- اجعل البصمة الأساسية للمصدر **SHA-256 من محتوى الملف نفسه**، لا من `name + size + lastModified`.
- إذا تعذّر حساب بصمة المحتوى تقنياً في حالة استثنائية فقط، استخدم metadata كحل احتياطي.
- عند رفع أكثر من ملف، اجعل البصمة المركبة **غير حساسة لترتيب الملفات**: احسب SHA-256 لكل ملف، رتّب البصمات ترتيباً ثابتاً، ثم ابنِ البصمة النهائية منها.
- لا تغيّر منطق خيارات «استبدال / إضافة على أي حال / إلغاء»؛ فقط اجعل اكتشاف المصدر نفسه أدق.

## 2. إعادة محاولة idempotency بعد النجاح

السيناريو المطلوب تغطيته:

> نجح الخادم في التوليد والخصم → انقطع اتصال العميل قبل استلام الرد → أعاد العميل نفس الطلب بنفس `X-Idempotency-Key` → يستلم النتيجة السابقة بلا خصم أو توليد جديد.

- إذا وصل طلب بنفس `X-Idempotency-Key` لعملية حالتها `completed` أو `succeeded`، **لا ترجع 409**، ولا تعِد التوليد، ولا تخصم نقاطاً جديدة.
- أعد `200` مع **نفس النتيجة المخزنة** للعملية السابقة كما هي، وبنفس شكل الاستجابة الذي تتوقعه الواجهة.
- لا تستدعِ مولد الذكاء الاصطناعي ثانية في هذه الحالة.
- إذا كانت الحالة `failed` أو `refunded` أو `failed_refunded`، يجوز رفض إعادة استخدام المفتاح برسالة مناسبة وطلب مفتاح جديد؛ لا تعِد تشغيل العملية بهذا المفتاح.
- أبقِ حماية الطلبات المتزامنة والحجز والـcapture والاسترداد الحالية كما هي.

## اختبارات مطلوبة

أضف اختبار تكامل صريح للحالة التالية:

1. الطلب الأول ينجح ويخصم مرة واحدة.
2. إعادة نفس `X-Idempotency-Key` بعد نجاح العملية ترجع `200` ونفس النتيجة المخزنة.
3. لا يحدث خصم إضافي.
4. لا يتم استدعاء مولد الذكاء الاصطناعي مرة ثانية.

وأضف اختباراً لبصمة الملفات غير الحساسة لترتيبها، واختباراً يثبت أن اسمين مختلفين للمحتوى نفسه ينتجان البصمة نفسها عند استعمال SHA-256.

شغّل الاختبارات وTypecheck، ثم أرسل تقريراً بالملفات المعدلة ونتائج الاختبارات فقط. لا تنشر.
